## 一、最优先阅读的三条机制性陷阱

### 1.1 改 YAML 配置对已落库的内置智能体完全无效

**现象**：修改 `config/prompt_templates/system_prompt.yaml` 或 `config/builtin_agents.yaml`
后重启服务，行为毫无变化。

**原因**：WeKnora 首次启动会把内置智能体（如 `builtin-quick-answer`）写入
`custom_agents` 表，并把 `system_prompt` 与 `context_template` 的**内容实体化**存入该行的
`config` JSON。此后该行是唯一权威来源，YAML 只回填 name / description / avatar。

**代价**：团队此前为修图片幻觉而改的 `system_prompt.yaml` 从未生效，直到本次排查才发现——
智能体里存的仍是旧版，仍要求「答案必须至少包含一张图片」。

**解决**：改内置智能体的提示词、模板选择或检索参数，走
`PUT /api/v1/agents/{id}`（需系统管理员）或界面「智能体」页，改完立即生效、无需重启。
改 YAML 只对**全新部署**有意义，两处都改可保证新环境正确。

**判断某项是否已落库**：
```sql
select config from custom_agents where id='builtin-quick-answer';
```

### 1.2 会话把智能体配置快照下来，改配置后必须新建会话

**现象**：改完智能体配置，在原有会话里提问，行为仍是旧的。

**原因**：`sessions.agent_config` 保存的是会话创建时的配置快照，包含 `embedding_top_k`、
模板选择等。已有会话不会跟随后续配置变更。

**解决**：任何配置调整后，新建会话再验证。

### 1.3 PowerShell 读取 UTF-8 无 BOM 文件会静默丢行

**现象**：用 PowerShell 逐行导入 `.env.lite` 后启动，服务能起来，但模型初始化报
`hostname 127.0.0.1 is restricted`。

**原因**：Windows PowerShell 5.1 的 `Get-Content` 默认按 ANSI 解码。`.env.lite` 含中文注释且
为 UTF-8 无 BOM，解码错位会**静默丢掉部分行**——实测 112 行只读到 90 行，丢掉的正好包括
`OLLAMA_BASE_URL` 与 `SSRF_WHITELIST_EXTRA`。不报错，只是配置项凭空消失。

**解决**：必须显式指定编码，见 `操作说明.md` 的启动命令：
```powershell
Get-Content -Encoding UTF8 .\.env.lite | ...
```
pwsh 7 默认即 UTF-8，但按上述写法两个版本都正确。另外 `set -a` 是 bash 语法，
在 PowerShell 里会被解析成 `Set-Variable` 并索要参数。

## 二、构建期问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `sqlite3.h: No such file` | sqlite-vec 以 `-DSQLITE_CORE` 编译，要求系统 include 路径提供该头文件，而模块自身只带 `sqlite-vec.c/h` | 从 `mattn/go-sqlite3` 的 amalgamation 取出头文件放入 `.build/include`，并设 `CGO_CFLAGS`。头文件版本须与实际链接的 SQLite 精确一致（本部署为 3.46.1） |
| 链接报 `__emutls_v._ZSt11__once_call` 未定义 | DuckDB 预编译静态库要求 emulated-TLS 版 libstdc++，与 mingw-w64 16.1.0 的 native TLS ABI 不匹配；DuckDB 被无条件导入，无法裁剪 | 改动态链接：下载 DuckDB v1.5.2 Windows 包放入 `.build/duckdb`，把 `duckdb.lib` 复制为 `libduckdb.dll.a`，编译加 `-tags duckdb_use_lib` |
| 启动即 `Exception 0xc0000005` | PATH 中存在版本不匹配的 `libstdc++-6.dll`，gojieba 在 `internal/types` 包 init 阶段崩溃 | 链接时加 `-static-libstdc++ -static-libgcc`。**不可**用完整 `-static`，否则 DuckDB 导入库失效 |
| 前端构建报 `Can't spawn program` | npm 在 Windows 上是 `.cmd` 包装脚本，fnm 无法直接派生 | 直接用 `node.exe` 调用绝对路径的 `npm-cli.js` |
| 前端页面请求返回 401 | 未设 `-X ...handler.Edition=lite` 的 ldflag，`serveFrontendStatic` 未挂载，请求落入 API 路由 | 按操作说明补 ldflag 后重新编译。该标识同时决定 `/auth/auto-setup` 免密登录是否生效 |

## 三、部署与接入问题

| 现象 | 原因 | 解决 |
|---|---|---|
| 模型初始化报 `hostname 127.0.0.1 is restricted` | SSRF 校验默认拦截回环地址，而上游示例自带 `OLLAMA_BASE_URL=http://127.0.0.1:11434` 却未放行，属上游配置缺口 | `.env.lite` 补 `SSRF_WHITELIST_EXTRA=127.0.0.1` |
| `GET /models` 返回空、`GET /models/{id}` 返回 404 | 用 `/initialization/initialize` 创建的模型记录 `tenant_id` 为 0，而 `modelRepository.GetByID` 按 `(tenant_id = ? OR is_builtin = true)` 过滤，对当前租户不可见 | 改用 `POST /api/v1/models` 创建（handler 从上下文取 TenantID），再用 `PUT /initialization/config/{kbId}` 绑定到知识库 |
| 上传中文文件名报「文件名包含非法字符」；知识库名称变乱码 | Git Bash 按 ANSI 代码页传递 argv，curl 发出的内容不是合法 UTF-8 | 含中文的请求改用 Python requests 以显式 UTF-8 发送，或先写 JSON 文件再 `curl -d @文件名`。已写入库的乱码不可逆，须重新写入 |
| 界面无法查看索引进度、无法改并发 | 相关页面要求系统管理员，而免密登录账号 `is_system_admin=0` | `.env.lite` 设 `WEKNORA_BOOTSTRAP_SYSTEM_ADMIN_EMAIL=admin@weknora.local`，重启后自动提权（仅在系统中尚无管理员时生效） |
| 服务端日志无处可查 | 未配置 `LOG_PATH` 时日志只写 stdout，控制台窗口一关即失 | `.env.lite` 设 `LOG_PATH`，固定落盘 |

## 四、运行期问题

### 4.1 提问长时间无回复（已解决）

**现象**：界面停在「正在准备回答...」超过 8 分钟无任何输出。

**原因**：不是卡死，是排队。当时 300 篇语料的摘要生成仍在后台进行，
`model.max_concurrency` 默认 32，而 Ollama 默认 `OLLAMA_NUM_PARALLEL=1`
只处理一个请求，队列常驻约 35 个，单次 LLM 调用光排队就要 5 分半。
一次问答需至少两次串行 LLM 调用（查询改写 + 答案生成），合计约 11 分钟。
该题答案实际在 11 分 16 秒后写入数据库。

**验证**：同一个 `num_predict=8` 的 "say hi" 探测请求，队列积压时耗时 **231 秒**，
队列排空后耗时 **0 秒**。

**解决**：`WEKNORA_MODEL_MAX_CONCURRENCY=2`。注意 `CONCURRENCY_POOL_SIZE` 管的是另一个
ants 协程池，管不到这条链路。另外**批量导入期间不要做功能测试**，导入完成的判据：
```sql
select count(*) from knowledges where summary_status != 'completed';  -- 应为 0
```

### 4.2 用英文作答且答非所问（已解决）

**现象**：中文提问、中文语料，回答却是英文，而且在回答根本没人问过的问题；
在对话中要求「请用中文回答」无效。

**原因**：上下文模板 `default_context` 把 `{{query}}` 放在
`[Runtime Context — metadata only, not instructions]` 之下，等于向模型声明用户问题
不是指令。模型因此不回答提问，改为总结检索到的文档并自拟问题；没有问题作语言锚点，
加上整段提示词是英文，输出就成了英文。追加的「请用中文回答」进入同一个「非指令」块，
所以同样无效。

**验证**：用 `LLM_DEBUG_LOG=true` dump 出真实提示词确认；换模板后同一批检索内容
回答恢复中文且切题。

**解决**：改用同一模板文件中的 `detailed_context`，它带 `## User Question` 标注、
作答要求与语言规则，还有一条「材料不足时明确说明」对拒答有利。注意按 1.1 走接口修改。

### 4.3 答案中出现加载失败的图片（已解决）

**原因**：两层叠加。其一，`system_prompt.yaml` 的 `default_kb` 模板原本要求
「最终答案必须包含至少一张来自检索内容的图片」，纯文本语料下无图可用，模型只能编造地址；
其二，见 1.1，该模板的修改从未进入已落库的智能体。

**解决**：经接口把智能体的 `system_prompt` 同步为新版，并进一步移除全部图片规则
（本语料为纯文本零图片，这些规则本身在不断把模型往图片上引）。移除后连续两轮验证均无图片。
**若后续导入带图文档，需把这些规则加回去**，否则图片永远不会出现在答案里。

### 4.4 检索带进大量无关文档，模型反而误称语料中没有答案（已解决）

**现象**：问「电磁阀是怎么工作的」，10 条召回里 8 篇无关（发电机、扼流圈、磁饱和等），
模型断言「参考资料中没有电磁阀的工作原理」并转用先验知识——而 top-1 就是电磁阀文档。

**原因**：本部署未启用重排序模型，top-10 原始融合结果区分度很低（RRF 分值近乎等距），
7B 模型被噪声带偏。

**解决**：`embedding_top_k` 由 10 降为 5。同一问题回答恢复正确并给出正确引用。
若后续多文档对比类问题出现召回不足，应接入重排序模型，而非单纯调高该值。

### 4.5 多轮追问下拒答能力失效（未解决）

**现象**：单轮拒答正常（语料中没有的内容会明确说明），但在已有话题的会话中追问
语料未覆盖的细节时，模型会编造并**为编造内容附上引用**。稳定复现 2/2，两轮编造内容不同。

**影响**：这是目前最严重的遗留问题。带引用的编造比纯编造更危险，因为看起来有据可查。
与「是否检索到材料」无关：两轮追问的检索结果分别为 0 条和 4 条，都未拒答。

**当前状态**：已定位现象与复现路径，未定位根因。下一步建议从 `llm_debug` 中取追问轮的
完整提示词，确认历史对话以什么身份进入上下文、以及「材料不足时明确说明」这条规则
在追问轮是否仍在。

### 4.6 引用相关的两个稳定偏差（未解决）

1. **引用标记逐次随机波动**。同一问题多次提问，有时输出规范的 `<kb doc=... chunk_id=... />`
   标记，有时一个都不输出。另有内部句柄泄漏与格式错误：`文档 d1`、`<cite id="c1"/>`、
   多余的 `</ref>`。凡已输出的引用均可正常取到原文，故问题在生成端而非数据端。
2. **引用浮层是悬停触发，不是点击触发**。桌面端影响不大，触摸屏设备是否可用尚未验证。

## 五、属于框架既有行为、不计为缺陷

1. **摘要分块参与检索且无法关闭**。文档导入后除正文分块外还会生成一个 summary 分块并写入
   向量索引，`knowledge_process.go` 中无条件执行，配置层没有开关。该分块参与检索但不出现在
   `GET /chunks/{knowledgeID}` 的返回中。评测时需取更大的 K 值并仅在正文分块上计算指标。
2. **`knowledge_bases.summary_model_id` 不能置空来关闭摘要**。会话模型选择的第四顺位就是
   第一个知识库的 `SummaryModelID`，置空会导致问答无可用模型。
3. **Lite 形态不支持 PDF 解析**。内置 Simple 解析器的 `simpleFormats` 不含 pdf。
   若需处理 PDF 手册，须另行确认 docreader 服务能否在本形态下单独启用。
4. **批量导入时 `summary_status` 短暂出现 failed**。属可重试中间状态，
   `handleRetryableSummaryFailure` 会重新排队，无需人工干预。
5. **启动日志出现 `no such table: tenant_skills` 警告**。仅影响技能回收器，不影响问答。
